# Инструкции для агентов

## Точки входа

- [`README.md`](README.md) — структура репозитория и общий обзор.
- [`CHANGES.md`](CHANGES.md) — история рефакторинга, метрики "было/стало".

## Стиль работы

- Перед началом работы в сессии - перечитай MEMORY.
- Действовать самостоятельно и минимизировать interruptions.
- Если найдена ошибка в роли - смотреть остальные роли тоже на предмет такой же ошибки, так как роли однотипные.
- Спрашивать перед destructive-действиями: `rm`, удаление плейбуков, переписывание inventory, массовые необратимые изменения.
- Каждая логическая фаза должна быть отдельным коммитом, если пользователь просит коммитить.
- После рефакторинга обновлять документацию: `README.md`, `AGENTS.MD`, `CHANGES.md`.
- В финальной сводке после крупной задачи указывать метрики "было/стало" и оставшиеся pre-existing проблемы.

## Что не делать

- Не коммитить файл с паролем vault (`.ansible.vault`, `vault_pass*`).
- Не использовать deprecated синтаксис: `with_items`, `include:` без `_tasks`/`_imports`, flat-syntax `module: a=b c=d`, `become: yes/no`.
- Не переписывать `shell:` на нативные модули.

## Контекст JiveFetch

JiveFetch — greenfield-проект кроссплатформенного GUI-менеджера медиазагрузок.
Целевой стек: Tauri 2, Rust, React и TypeScript; внешние движки — `yt-dlp`,
`ffmpeg`/`ffprobe` и опционально `aria2`.

Основные проектные документы:

- [`README.md`](README.md) — назначение, границы MVP и навигация.
- [`docs/product-requirements.md`](docs/product-requirements.md) — требования и критерии приёмки.
- [`docs/architecture.md`](docs/architecture.md) — компоненты и зависимости.
- [`docs/task-lifecycle.md`](docs/task-lifecycle.md) — состояния задач, восстановление и команды.
- [`docs/security.md`](docs/security.md) — cookies, секреты и модель угроз.
- [`docs/packaging.md`](docs/packaging.md) — sidecar-инструменты и выпуск под разные ОС.
- [`docs/licensing.md`](docs/licensing.md) — Apache-2.0 и gate сторонних движков.
- [`docs/roadmap.md`](docs/roadmap.md) — поэтапный план реализации.
- [`MEMORY.md`](MEMORY.md) — проверенные решения и точка продолжения.

## Правила разработки JiveFetch

- Перед изменениями читать `MEMORY.md` и релевантные документы из `docs/`.
- Держать бизнес-логику очереди, состояния задач и управление процессами в Rust;
  React является представлением и не должен быть вторым источником истины.
- Все переходы состояния задачи выполнять через один scheduler и сохранять в
  SQLite транзакционно до публикации события в UI.
- Не считать PID достаточным доказательством владения процессом. Завершать только
  созданное JiveFetch дерево: process group/session на Unix и Job Object на Windows.
- Не завершать процессы по имени (`yt-dlp`, `ffmpeg`, `aria2c`) и не применять
  глобальные `killall`/`taskkill /IM`.
- Pause/Resume должны иметь одинаковую переносимую семантику: контролируемая
  остановка с сохранением partial-файлов и новый resumable attempt. OS-specific
  suspend допустим только как дополнительная оптимизация, не как основной контракт.
- Не передавать shell-строки из UI. Аргументы внешних процессов строить как
  типизированный список в Rust; пользовательские URL и шаблоны не интерполировать
  в shell.
- Cookie-файлы, токены, заголовки авторизации, расшифрованные временные файлы,
  профили браузеров и URL с секретными query-параметрами не логировать и не
  коммитить.
- Секреты хранить через системное хранилище учётных данных; крупные cookie-данные
  шифровать случайным ключом, который хранится в keychain/credential store.
- Миграции SQLite должны быть вперёд-совместимыми, тестируемыми и не разрушать
  существующую очередь. Изменение схемы сопровождается recovery-тестом.
- Новая функция очереди обязана иметь тест переходов состояния и хотя бы один
  crash/restart сценарий. Управление процессами проверять отдельными helper-процессами,
  не реальными массовыми загрузками.
- Изменения packaging проверять на каждой заявленной ОС в native CI; локальная
  сборка одной ОС не подтверждает кроссплатформенность.
- Release tag должен совпадать с версиями приложения и пакетов. До прохождения
  signing, notarization, лицензирования sidecars и release gates выпуск помечать
  как pre-release.
- MediaHarbor и FlowGrab использовать только как публичные исследовательские
  ориентиры. Не копировать их код, ресурсы, тексты интерфейса или внутреннюю
  структуру; заимствованные идеи описывать как собственные требования.
- Приватный `origin` настроен. Commit или `push` выполнять только по прямой просьбе
  пользователя и после успешных релевантных проверок.

## Документация и проверка

- Архитектурное решение, меняющее публичный контракт, фиксировать в `docs/` до или
  вместе с реализацией.
- После рефакторинга обновлять `README.md`, этот `AGENTS.md`, `CHANGES.md` и
  `MEMORY.md`, когда изменились команды, структура, инварианты или точка продолжения.
- Не писать в README команды, которых ещё нет в репозитории. Планируемые команды
  явно помечать как будущие.
- Любой Markdown-документ поддерживать в полных EN/RU/简体中文 версиях. В начале
  каждой версии должны быть прямые ссылки на остальные два перевода.
- Любая пользовательская строка приложения должна проходить через словарь i18n.
  Первый запуск использует EN; явно выбранный RU или 简体中文 сохраняется локально.
- При изменении смысла документа или UI-строки обновлять все три языка в одной фазе;
  неполный набор переводов считается незавершённой работой.
- Перед итогом выполнять максимально доступный набор: форматирование, lint,
  unit/integration tests, `git diff --check`, проверку относительных Markdown-ссылок
  и поиск случайно добавленных секретов.
